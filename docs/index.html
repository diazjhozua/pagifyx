pagifyx code structure

pagifyx turns an existing company website into a print-ready brochure. It reads the site with a browser, asks an AI model to plan the brochure, lets the user revise the plan in a chat, and then writes a .docx file the user can edit in Word.

This guide explains how the code is organized. Read the first two sections for the shape of the system. Read the module reference when you need to change something.

Run it

uv python install 3.12
uv sync
uv run playwright install chromium
# copy .env.template to .env, then set LLM_BASE_URL, LLM_API_KEY, LLM_MODEL
uv run pagifyx            # open http://127.0.0.1:8000

The app will not start without the three LLM_* values. Set them in .env or in the environment. Environment variables take precedence over .env. The optional OUTPUT_DIR sets where generated files go. It defaults to output.

The big picture

The code is layered, and imports point downward. core imports only other core modules. reading, llm, and output import only from the layers below them. workflow imports core, reading, llm, and output. The web layer knows about HTTP. Its routes use core for types and fold helpers, and llm and reading only for their error classes. app.py imports llm to build the default client. No module below workflow imports workflow, and no module below web imports web.

Browser Forms, redirects, the proof sheet, the downloaded .docx
web/routes.py Routes. Reads form input, calls the service, redirects. Returns HTML or files.
workflow/service.py The brochure workflow. Each step locks the session, computes its results, and commits them only on success.
Collaborators: each does one job reading/scraper.py llm/client.py + llm/prompts.py reading/assets.py core/theme.py core/brand.py core/folds.py core/grounding.py output/docx_builder.py workflow/session.py
Foundations: used by everything above core/models.py reading/images.py core/fonts.py core/config.py

Three rules keep this clean. The scraper never touches the disk. The docx builder never calls the model. The routes never call Playwright or the model directly.

The user journey

Each step is one HTTP POST that calls one service method. The pages are GET routes: GET / (the start page), GET /sessions/{id} (the settings page), GET /sessions/{id}/overview (the proof sheet), GET /sessions/{id}/download (the .docx), and GET /sessions/{id}/files/{filename} (an image or the logo from the session's assets folder only). The lists below show the call chain for each step. For a phase-by-phase diagram, see the end-to-end flow.

1. Read the website

POST /sessions with a URL, or POST /sessions/{id}/retry to read again.

  1. web.create_session creates a Session and calls service.read_website. The retry route calls the same method on the existing session.
  2. scraper.scrape_site checks robots.txt first. It then opens the homepage in headless Chromium, takes the logo screenshot, and follows up to 5 same-domain links from the nav, header, and footer. It returns a SiteSnapshot.
  3. BrochureService._analyze asks the model for a SiteAnalysis. The site text sent to the model is capped at 12,000 characters.
  4. service._download_assets downloads the best images (images.select_images, then assets.download_images). It stores the logo screenshot with assets.store_logo. When no usable screenshot is stored, it downloads the og:image instead.
  5. read_website computes the colour candidates (theme.candidate_colours) and the font (theme.detect_font_family) from the styles the scraper collected. Session.commit_read then stores everything, clears any plan from the previous read, and deletes the previous read's files. It never deletes an uploaded logo.

Images and the logo are downloaded only after the model succeeds. Each read writes its files under a new prefix, so the previous read stays in place until the new one commits.

Fallback: POST /sessions/{id}/paste analyzes text the user pasted when the site blocks the reader. It makes one model call. The read has no images and no logo, and the only colour candidate is the default #1F4E79. With no detected font, the theme uses Calibri.

2. Choose a fold and generate the overview

POST /sessions/{id}/fold with the fold, brand, contact, and theme fields, and an optional logo file.

  1. web.choose_fold stores the typed values in session.settings_form, so the settings page can show them again after a failed step. It parses the fold (blank lets the model choose), builds ThemeOverrides and BrandOverrides (with contact details) through the build_*_overrides helpers in workflow/service.py, and reads the logo upload.
  2. service.choose_fold checks the logo upload before any model call. It must be 5 MB or smaller and a PNG or JPEG that Word can embed. Then it takes the session lock and builds the plan request with prompts.plan_request.
  3. The model reply goes through the plan check in service._plan_check. The reply must use the chosen fold. It must pass folds.check_plan, which checks the panel count, exactly one Cover as the last outside panel, Contact at most once and only with contact details, a headline on every panel except Gallery, an image on every Gallery panel, and known images used at most once. Its primary and accent colours must come from the website's colour list. It must also pass grounding.check_grounding, so every number and email in the panel text must appear in the website text or the form.
  4. Only after success does the service save the logo upload as logo-upload-<8 hex>.<ext>, delete the previous uploaded logo if the new one replaces it, and store the fold, overrides, overview, and chat history. A failed step writes no logo file, and the logo in use stays.

3. Revise in chat

POST /sessions/{id}/revise with a change request.

  1. service.revise sends the full chat history plus the request (prompts.revision_request) to the model. The reply goes through the same plan check, with the same fold.
  2. On success it replaces the overview, appends the note text to revisions, adds the exchange to the history, and clears brochure_path. The earlier .docx is then no longer offered for download.

4. Approve and download

POST /sessions/{id}/approve, then GET /sessions/{id}/download.

  1. service.approve makes no model call. It resolves the theme with theme.resolve_theme, which applies the theme overrides first. It then calls docx_builder.build_brochure with the overview, the fold spec, the brand (name, tagline, and effective logo), the theme, and the image files.
  2. The builder splits the panels into two faces with folds.face_panels. It writes one landscape Letter section per face, with one table per face.
  3. The download route serves the file at output/<session>/brochure.docx by default.

Model calls and retries

  • Read: one model call. A second call happens only when the reply does not parse or fails validation.
  • Plan and revise: one model call. A second call happens only when the reply does not parse, fails validation, or fails the plan check. The retry sends the rejected reply and the error text.
  • Approve: no model call.
  • A request error or an empty reply raises LLMError at once, with no retry. If the retry also fails, the step raises LLMError.

llm/client.py Wraps the OpenAI-compatible Chat Completions API. complete_json() asks for JSON, validates it with pydantic and an optional check, and retries once with the error text. Request errors and empty replies raise LLMError at once. ChatClient, LLMError

core/brand.py Brand identity helpers: picks the logo element from candidates and holds the user's brand overrides: name, tagline, logo, and contact details (phone, email, address). choose_logo(), BrandOverrides, LogoHint
core/theme.py The visual system: palette and font. Turns the site's colours into candidates and its font into a detected family, applies overrides, and produces the Theme used by the builder. Theme, Palette, ThemeOverrides, resolve_theme(), build_palette(), candidate_colours(), detect_font_family()
core/fonts.py Checks which font families are installed on Windows (registry). Falls back to Calibri when the site font is missing or on other systems. resolve_font(), installed_font_families()
core/folds.py The fold layouts: how many panels each side has. The model chooses the fold; check_plan() checks a plan against it: the panel count, one Cover as the last outside panel, Contact rules, a headline on every panel except Gallery, an image on every Gallery panel, and image ids that must be known and used at most once. core/grounding.py Checks that every number and email in a panel's headline or body appears in the website text or the form. A failed check makes the model retry. check_grounding(), unsupported_details()
core/models.py The data shapes exchanged with the model and used by the builder. Null values from the model become empty text, empty lists, empty objects, or false, depending on the field. FoldType, PanelSection, Preset, Design, Panel, Overview, SiteAnalysis, Contact, LOGO_IMAGE_ID
output/docx_builder.py Writes the brochure: landscape Letter, one section per face, one table per face with one column per panel. The preset decides the fills and text colours (see Presets under Key ideas). build_brochure(), BrochureBrand

Key ideas

Theme and Brand are separate

Theme is the visual system: palette and font. It lives in core/theme.py. Brand is the identity: name, tagline, logo, and contact details (phone, email, address). It lives in core/brand.py and core/models.py. The form, the overrides, and the docx builder keep the two apart. The terms are listed in CLAUDE.md.

Presets

The model picks one preset from the website's own look: full-colour for a site with a strong brand colour, night for a dark site, and paper for a light, neutral one. The table lists each preset, the label the web interface shows, and what the .docx does with it.

Preset (core/models.py)Label in the web UI (web/routes.py)What the .docx shows
Preset.FULL_COLOUR, full-colour Full colour The cover and call to action have a solid primary fill, with text in paper or ink, whichever contrasts more. Other panels are paper, with ink body text and primary headlines.
Preset.NIGHT, night Night The cover and call to action have a solid primary fill. Other panels are ink, with paper body text. Headlines use the accent colour when it reads on ink, and paper otherwise.
Preset.PAPER, paper Paper Every panel is on paper. The cover and call to action have primary text and no fill. Each headline except the cover's has an accent rule under it. Body text is ink.

The primary colour in the .docx can be darker than the website's colour. The palette darkens it only until paper-coloured text reaches 4.5:1 contrast on it.

Folds have faces

A brochure is a sheet with two sides, and each side is a row of panels. A FoldSpec fixes how many panels each side has. The model chooses which sections fill them, in print order: the outside side left to right, then the inside side. The cover is always the last panel on the outside side, which puts it on the outside right, next to the back.

A plan must fit its fold and its source

The model returns one plan: a fold, a design, and the panels. The service checks the reply against the chosen fold, folds.check_plan(), the website colour list, and grounding.check_grounding(). check_grounding() rejects any number or email in a panel's headline or body that is not in the website text or the form. The primary and accent colours must come from the website's own list, and the accent may be empty. A failed check makes the model retry once, with the error text.

Steps commit only on success

Every service method that changes a session runs under session.lock. The steps that call the model compute the new fold, overview, and history in local variables. They assign them to the session only after the model call succeeds. A failed call therefore never leaves a mismatched plan, such as the old overview paired with a new fold.

The settings form is the one exception. web.choose_fold writes session.settings_form before the step, so the settings page can show what the user typed after a failure.

Errors are shown, not raised

Workflow errors (ScrapeError, LLMError, BrochureError) are caught by web._attempt(). The message is stored on the session and shown on the next page. Anything else is a bug and surfaces as a server error.

The scraper only reads

scrape_site() returns a SiteSnapshot. That is raw page text, colours, fonts, image candidates, and a logo screenshot as bytes. It writes no files. Saving files is the job of reading/assets.py, which _download_assets in workflow/service.py calls. That function also handles the og:image fallback. This keeps the browser code easy to test and replace.

Fallbacks

  • Blocked site: the user can paste the site's text instead. The pasted path has no images, no logo, the default colour #1F4E79 as its only candidate, and Calibri unless the user sets a font.
  • No logo captured: the og:image is downloaded and used if it is a PNG or JPEG.
  • Site font not installed (or not on Windows): Calibri is used.
  • Model returns null: treated as empty text, an empty list, an empty object, or false, depending on the field.

Tests

The tests run offline. The model is replaced by a scripted fake (the make_chat fixture in conftest.py). The browser is replaced by a monkeypatched scrape_site. Run them with uv run pytest. The suite has 90 tests.

Common changes

Swap the AI provider

Edit .env only: LLM_BASE_URL, LLM_API_KEY, LLM_MODEL. The endpoint must support Chat Completions.

Add a fold

  1. Add the member to FoldType in core/models.py.
  2. Add a FoldSpec with its label, description, and panels_per_side to FOLD_SPECS in core/folds.py. The settings page calls get_fold_spec() for every FoldType, so a member without a spec breaks that page.
  3. In llm/prompts.py, add the panel count to _PANEL_COUNTS. It repeats the count from FOLD_SPECS, and a fold the user picks raises KeyError without it. Also add the fold to the fold rule in plan_request, which names the folds the model may choose.
  4. Add tests to tests/core/test_folds.py. The builder takes the panel split from the FoldSpec, so output/docx_builder.py needs no change unless the new fold prints differently.

Add or change a panel section

  1. Add the member to PanelSection in core/models.py.
  2. There is no per-fold map of sections. The model chooses the sections for each panel. Add the section to the list in plan_request (llm/prompts.py), and say there what the section needs.
  3. Add any special handling the section needs. check_plan in core/folds.py enforces the Cover slot, the Contact rules, and the Gallery image. Every other panel needs a headline. output/docx_builder.py special-cases Cover and Gallery. Cover and Call to action take the emphasis colours through _EMPHASISED. A new section otherwise gets the default look.
  4. Update the tests that use sections, in tests/core/test_folds.py and tests/output/test_docx_builder.py. Update the copy rules in llm/prompts.py if the section needs guidance.

Add a brand or theme override

  1. Add the field to BrandOverrides (core/brand.py) or ThemeOverrides (core/theme.py).
  2. Add the form field to web/templates/session.html.
  3. Add a Form parameter to choose_fold in web/routes.py, and add the field to the settings_form dict in the same function. The settings page reads that dict back after a failed step, so a missing key loses what the user typed.
  4. Pass the value to the build_brand_overrides() or build_theme_overrides() helper in workflow/service.py, and validate it there.
  5. Apply it where the value is used. Brand name and tagline go through brand_text(), which the plan and service.approve both use. Contact details go through _with_overrides() and _sources(). Theme values go through theme.resolve_theme.

Change what the model is asked to do

Edit the prompts in llm/prompts.py. Keep the JSON shape in sync with core/models.py. Pydantic rejects any other shape, and the client retries once with the error text.

Known gaps

  • The Z-fold .docx is identical to the tri-fold. The "panels fold opposite ways" instruction is not printed.
  • Inside faces look sparse when the site has little copy or few images. The lower half of a panel stays empty.
  • The generated flag is the model's own judgment. Code checks numbers and emails only, not invented claims. In practice the model marks almost every panel as generated.
  • Sessions live in memory and are lost when the server restarts.
  • Image checks read file headers only. A truncated image can still embed.
  • Font detection only works on Windows. Elsewhere every site font falls back to Calibri.
  • Logo capture only looks at images and SVGs in the header or nav, images and SVGs inside an element whose class contains "logo", and images whose alt text contains "logo". It considers the first six matches. Other sites fall back to the og:image.
  • A dark logo on a dark cover has little contrast.
