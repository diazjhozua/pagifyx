pagifyx code structure

pagifyx turns an existing company website into a print-ready brochure. It reads the site with a browser, asks an AI model to plan the brochure, lets the user revise the plan in a chat, and then writes a .docx file the user can edit in Word.

This guide explains how the code is organized. Read the first two sections for the shape of the system. Read the module reference when you need to change something.

Run it

uv python install 3.12
uv sync
uv run playwright install chromium
# copy .env.template to .env, then set LLM_BASE_URL, LLM_API_KEY, LLM_MODEL
uv run pagifyx            # open http://127.0.0.1:8000

The app will not start without the three LLM_* values in .env.

The big picture

The code is layered. Each layer only talks to the layer directly below it. The web layer knows about HTTP. The service layer knows about the workflow. The layers below do one job each and know nothing about the web or the workflow.

Browser Forms, redirects, the overview cards, the downloaded .docx
web/routes.py Routes. Reads form input, calls the service, redirects. Returns HTML or files.
workflow/service.py The brochure workflow. Each step locks the session, computes its results, and commits them only on success.
Collaborators: each does one job reading/scraper.py llm/client.py + llm/prompts.py reading/assets.py core/theme.py core/brand.py core/folds.py output/docx_builder.py workflow/session.py
Foundations: used by everything above core/models.py reading/images.py core/fonts.py core/config.py

Three rules keep this clean. The scraper never touches the disk. The docx builder never calls the model. The routes never call Playwright or the model directly.

The user journey

Every user action is one HTTP request. Each request maps to one service method. The tables below show the call chain for each step. For a phase-by-phase diagram with the function and line number for every step, see the end-to-end flow.

1. Read the website

POST /sessions with a URL, or POST /sessions/{id}/retry.

  1. web.create_session creates a Session and calls service.read_website.
  2. scraper.scrape_site opens the homepage and up to 5 same-domain nav links in headless Chromium. It returns a SiteSnapshot. It checks robots.txt first.
  3. assets.download_images keeps the best images (see images.select_images). assets.store_logo saves the logo mark, or the og:image if there is no logo element.
  4. theme.candidate_colours and theme.detect_font_family read the computed styles collected by the scraper. The plan picks its colours from the candidates.
  5. BrochureService._analyze asks the model for a SiteAnalysis through ChatClient.complete_json.

Fallback: POST /sessions/{id}/paste analyzes text the user pasted when the site blocks the reader.

2. Choose a fold and generate the overview

POST /sessions/{id}/fold with the fold, brand, and theme fields.

  1. web.choose_fold reads the fold (blank lets the model choose), saves the logo upload if there is one, and builds BrandOverrides (with contact details) and ThemeOverrides through the helpers in workflow/service.py.
  2. service.choose_fold takes the session lock and builds the plan request with prompts.plan_request.
  3. The model reply is validated by folds.check_plan and grounding.check_grounding. The panel count must match the fold, and every number or email must appear in the website text or the form.
  4. Only after success does the service store the fold, overrides, overview, and chat history. A failed attempt leaves the previous plan in place.

3. Revise in chat

POST /sessions/{id}/revise with a change request.

  1. service.revise sends the full history plus the new request to the model.
  2. On success it replaces the overview, appends the request to revisions, and clears the download link for any earlier .docx.

4. Approve and download

POST /sessions/{id}/approve, then GET /sessions/{id}/download.

  1. service.approve calls docx_builder.build_brochure with the brand, the resolved theme, and the image files.
  2. The builder splits the panels into two faces with folds.face_panels. It writes one landscape Letter section and one table per face.
  3. The route serves output/<session>/brochure.docx.

Module reference

Listed roughly from the top of the stack to the bottom.

ModuleWhat it doesKey names
web/app.py Builds the FastAPI app. Stores the shared parts (store, service, templates) on app.state.deps. Mounts static files and the router. create_app()
__main__.py Starts uvicorn on 127.0.0.1:8000 with the app factory. main()
web/routes.py One route per user action. Validates form input and maps workflow errors to a message on the session. Redirects with 303 after each POST. router, Deps, _attempt(), choose_fold()
workflow/service.py The workflow. Each method holds session.lock, computes new state in local variables, and commits only after the model call succeeds. BrochureService, BrochureError, build_theme_overrides()
workflow/session.py All state for one brochure: URL, analysis, images, overrides, fold, overview, chat history, revisions, output path, pending error. The store is a dictionary in memory. Session, SessionStore, clear_plan(), image_paths()
llm/client.py Wraps the OpenAI-compatible Chat Completions API. complete_json() asks for JSON, validates it with pydantic and an optional check, and retries once with the error text. ChatClient, LLMError
llm/prompts.py The system prompt and the message builders for analysis, overview, and revision. Brochure copy rules live here. SYSTEM_PROMPT, plan_request(), revision_request()
reading/scraper.py Reads the site with Playwright. Checks robots.txt, follows up to 5 same-domain links from nav, header, and footer, takes a logo screenshot, and collects colors, fonts, and image candidates. Writes no files. scrape_site(), SiteSnapshot, ScrapeError
reading/assets.py Downloads images and stores logos. Only files python-docx can embed are kept. download_images(), store_logo(), ImageAsset
reading/images.py Chooses which images suit a brochure: at least 400 px wide, at most 8, largest first. Drops SVG, favicon, and tracking images. select_images(), is_embeddable(), sniff_image_type()
core/brand.py Brand identity helpers: picks the logo element from candidates and holds the user's brand overrides (name, tagline, logo). choose_logo(), BrandOverrides, LogoHint
core/theme.py The visual system: palette and font. Detects them from computed styles, applies overrides, and produces the Theme used by the builder. Theme, Palette, ThemeOverrides, resolve_theme(), build_palette(), candidate_colours()
core/fonts.py Checks which font families are installed on Windows (registry). Falls back to Calibri when the site font is missing or on other systems. resolve_font(), installed_font_families()
core/folds.py The fold layouts: how many panels each side has. The model chooses the fold; check_plan() checks a plan against it. FoldSpec, FOLD_SPECS, get_fold_spec(), check_plan(), face_panels()
core/grounding.py Checks that every number and email in a plan appears in the website text or the form. A failed check makes the model retry. check_grounding(), unsupported_details()
core/models.py The data shapes exchanged with the model and used by the builder. Null values from the model become empty strings or lists. FoldType, PanelSection, Preset, Design, Panel, Overview, SiteAnalysis, LOGO_IMAGE_ID
output/docx_builder.py Writes the brochure. Landscape Letter, one section per face, one table per face with one column per panel. The cover is shaded with the primary color. build_brochure(), BrochureBrand
core/config.py Reads .env and the environment into a Settings object. Settings, get_settings()
web/templates/ and web/static/ Jinja2 pages (base, index, session, overview) and one stylesheet. session.html, overview.html

Key ideas

Theme and Brand are separate

Theme is the visual system: palette and font. It lives in core/theme.py. Brand is the identity: name, tagline, and logo. It lives in core/brand.py and core/models.py. The form, the overrides, and the docx builder keep the two apart. The vocabulary is defined in GLOSSARY.md.

Folds have faces

A brochure is a sheet with two sides, and each side is a row of panels. A FoldSpec fixes how many panels each side has. The model chooses which sections fill them, in print order: the outside side left to right, then the inside side. The cover is always the last panel on the outside side, which puts it on the outside right, next to the back.

A plan must fit its fold and its source

The model returns one plan: a fold, a design, and the panels. check_plan() rejects a wrong panel count, a cover in the wrong place, a Contact panel without contact details, and unknown or repeated images. check_grounding() rejects any number or email that is not in the website text or the form. The colours must come from the website's own list. The model gets one retry with the error text.

Steps commit only on success

Every service method that changes a session runs under session.lock. It computes the new fold, overview, and history in local variables. It assigns them to the session only after the model call succeeds. A failed call therefore never leaves a mismatched plan, such as the old overview paired with a new fold.

Errors are shown, not raised

Workflow errors (ScrapeError, LLMError, BrochureError) are caught by web._attempt(). The message is stored on the session and shown on the next page. Anything else is a bug and surfaces as a server error.

The scraper only reads

scrape_site() returns a SiteSnapshot. That is raw page text, colors, fonts, image candidates, and a logo screenshot as bytes. Saving files is reading/assets.py's job. This keeps the browser code easy to test and replace.

Fallbacks

  • Blocked site: the user can paste the site's text instead.
  • No logo element: the og:image is used.
  • Site font not installed (or not on Windows): Calibri is used.
  • Model returns null: treated as an empty string or list.

Tests

The tests run offline. The model is replaced by a scripted fake (the make_chat fixture in conftest.py). The browser is replaced by a monkeypatched scrape_site. Run them with uv run pytest.

Common changes

Swap the AI provider

Edit .env only: LLM_BASE_URL, LLM_API_KEY, LLM_MODEL. The endpoint must support Chat Completions.

Add a fold

  1. Add a member to FoldType in core/folds.py.
  2. Add a value to FoldType, a FoldSpec with its panels_per_side, and list it in the fold rule of plan_request.
  3. Add a test in core/test_folds.py. The builder reads the plan and the spec, so the only other files that change are the prompt and the fold list.

Add or change a panel section

  1. Add the member to PanelSection in core/models.py.
  2. Place it on a face in each fold that uses it. The prompt and the builder pick it up from there.
  3. Update the tests that list sections, and the copy rules in llm/prompts.py, if the new section needs guidance.

Add a brand or theme override

  1. Add the field to BrandOverrides (core/brand.py) or ThemeOverrides (core/theme.py).
  2. Add the form field to web/templates/session.html.
  3. Read it in web.choose_fold, validate it in the build_*_overrides helpers in workflow/service.py, and apply it where the value is used (service.approve or theme.resolve_theme).

Change what the model is asked to do

Edit the prompts in llm/prompts.py. Keep the JSON shape in sync with core/models.py, because pydantic rejects anything else and the model gets one retry.

Known gaps

  • The Z-fold .docx is identical to the tri-fold. The "panels fold opposite ways" instruction is not printed.
  • Inside faces look sparse when the site has little copy or few images. The lower half of a panel stays empty.
  • The generated flag is the model's own judgment. Code checks numbers and emails only, not invented claims.
  • Sessions live in memory and are lost when the server restarts.
  • Image checks read file headers only. A truncated image can still embed.
  • Font detection only works on Windows. Elsewhere every site font falls back to Calibri.
